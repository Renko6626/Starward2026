# 完整作品投稿、版本与审核设计

日期：2026-10-31。业务规则及技术路线已在本次讨论中获得用户确认；后续已获授权在 `feat/submission-and-review` 实施。本文记录设计，实际验证及实施细化见配套计划末尾的执行记录。

## 目标与已确认规则

1. 收取完整成品，作品形式可不同，支持一份作品包含多个文件。
2. 每次正式提交都是一个完整版本。上传文件不等于正式提交；点击提交后，版本内容固定。
3. 暂不设置首交或修订的时间 cutoff，不因活动开始、结束或旧截止日期自动禁止投稿。
4. 首次审核通过的完整版本是审核基准。之后的小修可以继续提交，沿用已有通过结论，并明确显示审核后有更新。明显改变内容时由主催决定复审。
5. 管理员能查看所有参与者的交稿情况、审核状态、最新完整版本、历史版本，并向具体版本写审稿意见。
6. 审稿意见保存后作者直接可见，不增加内部备注、意见发布审批或邮件通知系统。
7. 上传、正式提交、版本查看、审核状态及意见均进入作者个人工作台 `/portal/`，位置醒目，最新意见直接展开。
8. 报名资格审核、作品内容审核和公开发布各有自己的含义。上传或内容审核通过均不自动等于已经按排期发布。

## 已选路线与取舍

沿用 React、TanStack Router、Hono、D1 和现有私有 R2。保留 `project_drafts` 作为一位参与者的一份作品容器，在其下增加完整投稿版本及版本审稿记录；现有文件记录关联到具体版本。

讨论过直接覆盖当前文件：存储少，但无法保留审核依据及对应意见。独立建立一套投稿系统会扩大边界、重复账号及作品关联。本次选择在现有结构内增加版本记录，代价是历史文件持续占用存储。

不增加对象存储供应商、S3 密钥、转码、在线编辑器、自动内容审核、版本差异算法、后台任务、提交恢复队列或复杂幂等协议。多次投稿仍按现有规则联系主催人工安排，不在本次改为一人多作品模型。

- 管理端仍按 `preview_status` / `review_status` 筛选，单个 `admin_feedback` 会覆盖旧意见；新流程改读版本及审稿记录。
- `published_at` 的数据库 CHECK、公开查询与自动发布仍依赖两项旧状态。本次不重建作品主表，不修改历史迁移；用集中、单向的公开投影对接现有发布链路，见下文。

## 作者工作台

审核通过报名或已完成参与的作者，在页面标题下、基本信息和创作意向之前看到独立的「作品提交与审核」主面板。它不依赖是否已有文件或上传窗口是否开放来决定是否显示。

面板顺序：

1. 状态：未提交、待审核、需修改、已通过或未通过；同时列出最新版本号、提交时间和当前结论依据的版本号。
2. 最新审稿意见：正文、针对版本和时间直接展开。需修改／未通过时使用醒目的反馈样式，不只藏在操作记录或历史折叠区里。
3. 最新正式版本：完整文件列表、下载、标题、类型、简介和版本说明。
4. 投稿编辑区：上传整套新文件，填写最终资料，按钮明确为「提交完整作品」或「提交新版本」。上传中、上传失败和文件尚未完成时不能正式提交。
5. 历史版本及历史意见：可折叠，用户主动展开后查看。首次通过版可直接定位。

首次进入尚无投稿的作者直接看到上传和提交入口；窗口手动关闭时仍能看作品与意见。待报名审核作者保留原报名流程，显示报名通过后可投稿的说明，不开放上传。

沿用工作台现有字体、配色和组件，不重做全站布局。桌面与手机都应在基本资料之前发现作品区；意见正文正常换行。目录增加到作品面板的锚点，旧 `/portal/project` 继续跳回工作台，不另建必须访问的作者页面。

## 完整版本与文件

- 文件先上传至现有 `work_files`，未提交时 `submission_id IS NULL`，作者可删除和重新上传。
- 正式提交请求明确列出这次完整版本的所有文件 ID。至少一个完成上传的文件；所有文件必须属于当前作品、未被其他版本使用、ID 不重复。
- 每次上传并提交完整的新文件集合，不隐式继承旧版本附件、不把几个增量文件自动拼成新稿，也不增加文件去重或跨版本引用机制。
- 提交成功后这些文件固定归属该版本，作者不能删除或改挂。删除接口在服务端拒绝已提交文件的删除。原有下载接口继续执行本人／管理员权限检查。
- 不要求可编辑源工程。允许各作品类型使用现有文件上传能力；本轮不新增强制文件后缀、视频时长或自动解析字数等限制。
- 版本内容固定包括：标题、最终作品类型、简介、选填版本说明、完整文件集合。正式发布链接不作为投稿必填项。
- 实施默认值：标题必填 1—120 字符；类型使用现有 `WorkType`；简介必填 1—1600 字符；版本说明选填、不超过 2000 字符。类型沿用现有枚举，混合作品可使用「其他」并在简介中说明。表单可将创作意向作为简介初值供作者确认，不能自动替作者提交。
- 封面、标签等现有公开资料可继续保留，本轮不扩成新的必填表单。

## 审核与意见

审稿记录追加保存，每条都关联一个明确版本。记录包含审稿正文、选填结论、管理员身份和时间。意见正文最多 2000 字符；仅保存意见时正文不能为空。

结论只有 `approved`（已通过）、`changes_requested`（需修改）、`rejected`（未通过）；不选结论即仅保存意见。需修改和未通过必须给出非空理由。无内部备注，不提供编辑或删除已发表意见的另一套流程；写错时追加更正意见。

管理员默认打开最新版本。历史版本可查看和追加意见；改变作品当前结论必须针对当时最新版本，旧页面提交结论时若已有新稿，提示刷新后再审，不自动重试或把结论套到新稿。

### 当前状态的唯一计算规则

`work_submissions` 和 `work_submission_reviews` 是正式投稿状态的权威来源；不再把旧双状态作为内容审核依据。

| 情况 | 工作台与后台显示 |
| --- | --- |
| 没有正式版本 | `not_submitted`，即未提交；已上传暂存文件不计为交稿 |
| 已提交，没有有效结论 | `pending`，即待审核 |
| 最新有效结论通过 | `approved`；若最新版本比依据版本新，附「审核后有更新」，不宣称新稿已被审核 |
| 最新稿被要求修改或未通过 | `changes_requested` 或 `rejected`，展示理由 |
| 需修改／未通过后再次提交完整新版 | `pending`，等待重新查看，历史通过记录不自动使其恢复通过 |
| 仅增加审稿意见 | 不改变上述结论 |

最新有效结论取审稿记录中最后一条有结论的记录。若新稿比该结论针对的版本新，且结论非通过，状态回到待审核。首次通过版始终保留为历史基准；若主催之后明确要求复审或判定不通过，当前结论随之变化，不能永远被第一次通过锁死。

已经公开的作品需要先使用现有撤下操作，再保存需修改／未通过的结论；沿用项目现有约束，不新增自动撤下流程。

## 管理端

继续使用 `/portal/admin/project-drafts` 及其详情页。列表默认展示已交稿但尚未通过的作品，包括待审核、需修改和未通过；切换「全部作品」可查看所有作者，包含已获参与资格但尚未提交的作者。以参与者为查询起点 LEFT JOIN 作品和最新投稿，不能因缺少文件或作品容器而漏人。没有容器时只显示未提交，进入已具资格作者详情时按现有初始化规则建立容器。

列：作者、作品标题／类型、接力时点、当前审核状态、最新版本／提交时间、结论依据版本、审核后更新标记。支持已交稿未通过、全部、未提交、待审核、需修改、已通过、未通过及审核后更新筛选，保留搜索和返回列表的筛选条件。

详情上方直接展示最新完整稿的文件下载；旁边或下方是当前结论与审稿表单，清楚写明正在针对 V几。历史版本和意见可展开，首次通过版有明确入口。文件按版本列出，不能再把所有历史文件混成「最新作品」列表。

## 数据与接口契约

新迁移 `migrations/0025_work_submissions.sql`（实施前如编号已占用，顺延且更新文档）：

- `work_submissions`：`id TEXT PRIMARY KEY`、`draft_id` 外键、`version_number INTEGER`、`title`、`work_type`、`summary`、`version_note`、`submitted_at`；`UNIQUE(draft_id, version_number)`。版本号从 1 顺序分配。
- `work_files.submission_id TEXT NULL REFERENCES work_submissions(id)`，建立索引。既有行保持 NULL，不搬动 R2 对象。
- `work_submission_reviews`：`id INTEGER PRIMARY KEY`、`submission_id` 外键、`feedback`、可空 `decision`、`reviewed_by`、`created_at`。用整数 ID 确定意见先后，不增加审核状态机表或缓存状态列。
- 外键沿作品容器现有生命周期，不引入删除已提交作品的业务入口。

作者 API：

| 接口 | 作用 |
| --- | --- |
| `GET /api/portal/project/submissions` | 当前状态摘要、最新版本、首次通过版摘要、全部版本摘要、最新意见、暂存文件及投稿开放状态 |
| `GET /api/portal/project/submissions/:submissionId` | 本人某版完整资料、文件及该版所有意见 |
| `POST /api/portal/project/submissions` | `{ title, workType, summary, versionNote?, fileIds }` 创建完整版本，返回刷新后的工作区 |

管理员 API：

| 接口 | 作用 |
| --- | --- |
| `GET /api/admin/project-drafts` | 扩展为上述统一状态与最新稿摘要；保留现有详情 URL |
| `GET /api/admin/project-drafts/:draftId/submissions` | 该作者的投稿工作区及历史摘要 |
| `GET /api/admin/project-drafts/:draftId/submissions/:submissionId` | 指定版本完整内容及意见 |
| `POST /api/admin/project-drafts/:draftId/submissions/:submissionId/reviews` | `{ feedback, decision? }` 追加公开给该作者的意见／结论，返回刷新后的工作区 |

`GET/POST/PUT/DELETE /api/portal/project/files...` 复用现有上传流程；作者文件列表只列暂存文件，已提交文件从版本详情读取。下载继续复用现有文件下载 URL。所有投稿接口沿用现有认证、参与资格和 Origin 校验；管理员沿用现有管理员权限。

## 不设 cutoff 与旧流程衔接

- 复用 `work_upload_open` 的手动启用开关及可选开始时间；关闭开关是主催主动暂停，不能由旧截止日期代替。
- 该窗口不再允许结束时间：迁移清空其 `closes_at`，后端拒绝设置非空结束时间，活动设置中去掉此窗口的结束时间输入。其他活动窗口照旧。
- 窗口关闭不妨碍读版本、审稿意见及本人／管理员下载，也不妨碍管理员审核。
- 取消作者工作台的作品截止倒计时。修改活动规则中硬性截止、入口日期承诺及依附该截止的次日补救表述；改成可提交完整作品、按排期尽早交稿、预计来不及则联系主催，不另设截止或自动惩罚。
- 作品投稿时限放宽不改变现有「首次公开发布确认仅在约定北京时间当天」规则，发布与投稿是不同动作。
- 关闭旧预告／审查保存和提交 API，以及后台旧双状态写入口，返回明确的 `410` 说明。旧编辑器不再恢复。
- 历史 `admin_feedback` 只在「历史资料审核意见」中展示，不伪造对应版本、正式内容审核结论或投稿时间。既有上传文件仍是暂存材料，由作者明确组成完整 V1 后提交。

### 对接现有公开流程的单向投影

为避免同时重建现有 D1 主表及其依赖，本次保留 `project_drafts` 的旧字段名和公开展示快照。它们服务现有公开页面与数据库 CHECK，不再是两套可独立操作的审核状态。

- 新审核结论统一写入审稿记录，再在同一 D1 batch 中将公开资格投影到旧字段：通过时两项旧状态均为 `approved`；未通过／需修改时均为 `changes_requested`。普通意见及新版本提交不写这些字段，待审核状态只从正式投稿记录计算。这样已有公开作品补交 V1 或小修时也不会触发旧 `published_at` CHECK 或丢失公开快照；历史旧通过状态不据此伪造新审稿记录。
- 审核通过时复制该版标题、类型、简介到现有公开展示字段；之后未复审的小修不自动覆盖公开快照，不会因作者改稿提前泄露新资料。
- 投影只有 `worker/data/work-submissions.ts` 的集中写路径维护。现有发布确认、自动公开和管理员公开操作都必须补上正式投稿当前状态为通过的校验，不能只凭旧双状态公开新作品。
- 已公开的历史作品保持可读，不强迫追溯补交。已有撤下记录继续阻止自动重新公开；新的手动重新公开仍应检查正式内容审核。
- 保留 `work_url`、`release_confirmed_at`、`published_at` 的现有语义与隐私选择。不自动公开私有文件、文件名、版本说明、审稿意见或管理员身份。

以上是为复用现有发布链路的有限适配；本次不增加独立预告流程，也不开展字段重命名及全表重建。未来如清理这些存储字段，另行评估迁移，不与本次功能捆绑。

## 可靠性与验证边界

这是低频活动工具。提交前使用现有上传完成检查，正式提交和文件归属在 D1 batch 内一起写入；版本固定及意见对应版本属于核心业务要求。版本或资料变化时提示刷新、人工重试，不新增请求队列、恢复状态、乐观更新系统或重复提交令牌。

沿用现有 SQLite D1 夹具和内存 R2，针对完整版本不可变、权限、审核与版本关系、无 cutoff、公开隐私和历史数据保留新增精简后端行为用例。文案和样式不新增永久测试。

页面只做桌面／手机静态截图检查；用现有本地夹具准备未提交、待审核、需修改和通过后更新的画面，不自动点击、填表或运行浏览器交互 E2E。现有受影响 E2E 的断言可随行为调整，但本次不执行；若要执行，需用户明确要求。

实施最终运行相关 Vitest、`npm run check`、`npm run build`，集中验证一次；修正只补查受影响项。计划阶段仅检查文档完整性，不声称功能已实现。部署、生产迁移、生产窗口开关均不在本次本地实施动作内。
