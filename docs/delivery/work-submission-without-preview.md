# 取消预告流程并统一正式作品提交

2026 年 10 月 11 日。用户确认这轮保留预告后端，只记录方案；本轮未删除预告字段、审核状态或发布约束。

后续作品流程围绕完成作品、填写最终 metadata、提供公开发布链接展开。独立的作品预告及预告审核流程应移除。当前工作台已经不挂载预告表单，后续无需兼容旧的作者填写流程，也无需为预告保留长期兼容层。现有 API 和数据库模型仍在，需要在一次集中清理中同步调整内部依赖。

## 已确认的工作台规则

- 报名、待审核和已通过作者共用前两章：基本信息、创作意向。后一章包含预计作品类型和简介；后续阶段往后追加章节，继续复用前两章。
- 已通过作者可以分别保存基本信息和创作意向。意向修改直接保存，保留报名审核结果、审核记录和已确认时段。
- 当前工作台不展示作品预告、审查说明及提前收集发布链接的表单，让作者专注创作。
- 已确认报名作者的页面最上方显示作品截止倒计时，复用主页的任务倒计时样式，目标为北京时间 2026 年 11 月 11 日 23:00。
- 第三章为接力安排，显示前后两棒，提供其 B 站主页链接复制入口。链接可见范围沿用现有邻居接口的资格限制。
- 第三章的调整或申请换期按钮放大并强调；顶部调整发布时间入口保持现状。

`preview_title` 和 `preview_summary` 同时用于公开作品标题、简介及最终作品展示。它们是需要迁移的 metadata，不能随预告状态一起删除。现有发布确认与站内公开也有不同时间，不能把 `release_confirmed_at` 和 `published_at` 合并。

## 推荐的数据迁移范围

沿用 React、Hono 和 D1。建议先保留现有作品表的 ID、参与者关联和时段关联，集中清理预告生命周期；本次无需增加存储服务或更换技术栈。

| 现有字段或配置 | 后续处理 |
| --- | --- |
| `preview_title`、`preview_summary` | 迁移为最终作品 `title`、`summary`，保留原值 |
| `preview_status`、`preview_submitted_at` | 从有效作品模型、查询和写入逻辑中删除 |
| `preview_submit_open` | 从有效活动配置、设置页面和校验中删除 |
| `work_type`、`format_label`、`public_tags_json` | 保留为作品 metadata |
| `cover_url`、`cover_alt` | 保留为封面 metadata，是否必填另行决定 |
| `work_url` | 保留为公开发布链接；B 站为常用来源，继续支持符合校验的其他 HTTPS 地址 |
| `release_confirmed_at`、`published_at` | 分别保留作者发布确认与站内公开时间 |
| `content_note`、`content_warnings`、`review_note`、`review_status` | 按正式作品审核的实际需要重新评估；不继续作为一套需要提前填写的审查说明表单 |

使用新的版本化迁移处理已有数据库，不修改已经执行的历史迁移。迁移前备份，并完整保留 metadata、作品 ID、作者和排期关系、已有公开时间及历史事件。涉及旧 CHECK 和字段关系的表重建，应在同一迁移中处理索引和外键。

历史事件可以继续展示原有操作记录，但新流程不再产生预告提交或预告审核事件。重命名最终作品字段时，应同步更新类型、序列化、管理端及公开端，避免长期保留两套名称。

## 推荐的接口和页面调整

当前 `PATCH /api/portal/project/preview`、`POST /api/portal/project/preview/submit` 承载了 metadata 保存和预告审核。建议将 metadata 保存统一到作品接口，移除预告专用写入口及校验。正式作品提交入口在下一阶段明确后接入，不让基础资料保存触发作品审核。

后台只保留正式作品管理所需的状态和操作。待审核计数、退回说明、公开检查和管理员撤下逻辑必须使用同一套最终作品规则。作者页面的新章节仅在相应阶段开放后追加，基本信息和创作意向不因新增作品资料章节而替换或迁移。

时间表的时间槽外观、布局和选中标记保持原样。取消预告后，只调整时间槽详情所读取的作品摘要数据及操作入口，不重做时间槽。

## 实施前需要确认的规则

1. 正式作品内容审核如何进行。现行活动规则仍要求正式作品审核；取消预告审核不自动等于取消正式作品审核。
2. 下一阶段何时开放，以及哪些 metadata 必填。建议以标题、作品类型、简介和发布链接为主要字段，封面、标签等按实际展示需要决定。
3. 发布链接能否提前保存。现有逻辑限制首次确认发生在作者约定的北京时间发布当天；需要区分链接草稿保存与发布确认。
4. 站内公开由管理员确认，还是在正式作品审核、metadata 和作者发布确认都满足条件后自动进行。保持已撤下作品不会因普通保存而再次自动公开。

这些规则确定后，再实施接口和模型调整。本轮工作台收敛不会替这些决策自动选定方案。

## 后续实施与验证顺序

1. 确认最终 metadata、正式作品审核及公开条件，补齐接口契约。
2. 编写版本化迁移，保留已有作品和关联数据；更新 D1 夹具及本地示例数据。
3. 同步修改后端保存、提交、审核、发布确认和公开读取逻辑，清理预告窗口和旧写入口。
4. 更新后台管理和公开展示；下一阶段开放后向作者工作台追加作品章节。
5. 复用现有作品、发布确认和协作测试，检查数据迁移后既有公开作品可读、metadata 不丢失、私人资料不泄露、匿名规则保留，以及并发换期和管理员撤下保护仍有效。

淘汰预告流程专属用例时，应保留它们覆盖的独立发布、权限和隐私约束；不能用删除断言或放宽预期掩盖行为回归。UI 默认通过截图检查，不自动填写或提交作者表单。
