# Production tag deployments

The workflow in [deploy-production.yml](../../.github/workflows/deploy-production.yml)
builds and deploys a newly pushed Git tag whose name ends in `-prod`, for example
`v1.0.0-prod`. It deploys the commit referenced by that tag, not the latest branch
commit. Branch pushes, other tags, tag updates and tag deletions do not deploy.
The workflow must exist in the tagged commit.

## Release sequence

1. Install dependencies from `package-lock.json` using Node 24.12.0.
2. Test the deployment checks and validate the production Wrangler configuration.
3. Regenerate station previews and orbital assets if the tagged source fails their
   freshness checks. CI installs Chromium and the pinned Python dependencies as
   needed; generated files are build artifacts and are not committed back to Git.
4. Run the application and station asset tests against the prepared release source.
5. Run the existing type checks, static asset freshness checks and Vite build with
   `CLOUDFLARE_ENV=production`.
6. Apply pending migrations to the production D1 `DB` binding.
7. Deploy the frontend and Worker together using the configuration generated by Vite.
8. Check the public homepage and `/api/health`, then write the tag, commit and URL
   to the Actions run summary.

The Cloudflare API token is available only to the credential, migration and
deployment steps. `wrangler deploy --keep-vars` preserves extra runtime variables
configured in the Cloudflare dashboard. Variables explicitly declared in
`env.production.vars` still take precedence. Worker secrets survive redeploys.

Production releases share one concurrency group and an active release is never
cancelled by a newer tag. GitHub may replace an older pending run when several
release tags arrive while a deployment is running; publish one release at a time.
A failed migration stops deployment. A failed smoke check marks the run failed,
but does not automatically roll back the Worker or database.

## One-time production configuration

Create a separate production D1 database in the target Cloudflare account. Update
`env.production` in [wrangler.jsonc](../../wrangler.jsonc):

- `name`: `starward2026-production` by default. Match the existing production
  Worker name if it has already been created.
- `d1_databases`: replace `REPLACE_WITH_PRODUCTION_D1_DATABASE_ID` with the
  production database UUID; set `database_name` to the actual database name.
  Keep `binding: "DB"`. The guard rejects the database used by staging.
- `vars.BETTER_AUTH_URL`: the real HTTPS origin, such as `https://event.your-domain.tld`,
  with no path, query or credentials.
- `routes`: add a matching Workers Custom Domain:

  `"routes": [{ "pattern": "event.your-domain.tld", "custom_domain": true }]`

- `ratelimits`: keep the two production bindings. The supplied namespace IDs
  `2026041103` and `2026041104` differ from staging; ensure they are not already
  used by another application in the same account.

The production domain's DNS zone must be active in the target Cloudflare account.
This workflow expects a Custom Domain. If deployment should use only
`workers.dev`, adjust the guard and URL configuration first.

Run `npm run check:production` to confirm these settings. The current production
placeholders deliberately fail this check until real resources are configured.

Configure the runtime separately for `starward2026-production`:

- Add `BETTER_AUTH_SECRET` as a Worker secret using the Cloudflare dashboard or
  `npx wrangler secret put BETTER_AUTH_SECRET --env production --config wrangler.jsonc`.
  Use a stable, random secret of at least 32 characters; do not regenerate it on each release.
- Configure Cloudflare Access for the admin paths, with
  `CLOUDFLARE_ACCESS_TEAM_DOMAIN` and `CLOUDFLARE_ACCESS_POLICY_AUD` on the Worker.
- For QQ login, set `QQ_OAUTH_ENABLED=true` in the production Wrangler vars,
  configure `QQ_APP_ID` and the `QQ_APP_KEY` Worker secret, and register the
  production callback. See [qq-oauth.md](qq-oauth.md).
- For email OTP, configure the `RESEND_API_KEY` Worker secret and
  `RESEND_FROM_EMAIL` (and optionally `RESEND_FROM_NAME`). Password login does
  not require Resend.
- Keep `ALLOW_LOCAL_ADMIN_BYPASS` and `ALLOW_LOCAL_DEV_ORIGINS` out of the deployed runtime.

GitHub's deployment token is for managing Cloudflare resources; it does not replace
these application runtime secrets. The workflow does not provision Access or QQ
applications and does not rotate runtime secrets. The smoke check confirms the
site and API are reachable; it does not test real user login, Access or QQ OAuth.

## Cloudflare API token

Create a dedicated API token using the **Edit Cloudflare Workers** template or a
custom token with these permissions:

| Scope | Permission | Purpose |
| --- | --- | --- |
| Account | Workers Scripts: Edit/Write | Upload and deploy the Worker and frontend assets |
| Account | D1: Edit/Write | Apply production database migrations |
| Zone | Workers Routes: Edit/Write | Configure the production Workers Custom Domain |
| Zone | Zone: Read | Resolve the production domain's zone |

Restrict account resources to the deployment account and zone resources to the
production domain's zone. With Cloudflare's granular Workers roles, use Editor
for an existing Worker; creating the initial Worker requires product-level Admin.
Do not use a Global API Key or put the token in a file committed to Git.

References: [Cloudflare GitHub Actions setup](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/),
[Workers permissions](https://developers.cloudflare.com/workers/authorization/workers/),
[API token permissions](https://developers.cloudflare.com/fundamentals/api/reference/permissions/).

## GitHub configuration

In the repository, open **Settings → Environments** and create `production`.
Allow deployment from tags matching `*-prod` (or a matching pattern that includes
any slash-separated release prefix you use). Leave required reviewers disabled
if releases must deploy automatically without approval.

In that environment, add these **secrets**:

| Secret | Value |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | The dedicated deployment API token |
| `CLOUDFLARE_ACCOUNT_ID` | The target Cloudflare account ID |

Repository Actions secrets of the same names also work. No GitHub personal access
token is required; the workflow uses a read-only built-in GitHub token to check out
the repository. Disable any separate Cloudflare branch-triggered production build
if this tag workflow should be the sole production release path.

## Publish a release

Commit and push the workflow and completed production configuration first. Then
create and push one new release tag:

```bash
git tag -a v1.0.0-prod -m "Production release v1.0.0"
git push origin v1.0.0-prod
```

For a failed run, fix the cause and use GitHub Actions **Re-run failed jobs** if the
same commit can be retried, or create a new release tag for a code/configuration
fix. Avoid force-moving release tags.

Migrations execute before the new Worker is deployed and do not roll back when a
Worker deployment fails. Before upgrading an existing database, review pending SQL
and establish a recovery point. In this repository, migration `0012` deliberately
replaces profile data and `0020` rebuilds nullable-email tables; see
[migrations/README.md](../../migrations/README.md). The workflow never resets or
seeds the production database. D1 records applied migrations so a retry applies
only those still pending. Application rollback must be compatible with the
already-applied schema.

More references: [Vite production environment selection](https://developers.cloudflare.com/workers/vite-plugin/reference/cloudflare-environments/),
[D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/),
[Wrangler deploy options](https://developers.cloudflare.com/workers/wrangler/commands/workers/).
